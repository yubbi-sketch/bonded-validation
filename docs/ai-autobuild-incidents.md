> 오너 통찰(2026-08-30): "AI가 전체를 다 만들 때 어디가 뚫리나를 우리 스스로에게 적용해 확인하는 방법."
> AI(Claude)가 자율로 지은 산출물을 적대적으로 털어, '지시는 옳게 따랐으나 상호작용에서 창발한' 보안 결함을 기록한다.
> 이건 앱 수리이자 담보 발화 연구의 실데이터다.

## INC-2026-08-30-01 — 담보 발화장(sejong-arena) 감사원장 오염
- **패턴(★ 창발)**: 두 요구를 **각각 옳게** 구현했으나 교차점에서 위험이 창발.
  - 요구 A(server): "누구나 무인증으로 도전한다" → 옳게 구현.
  - 요구 B(db): "감사로그는 수정·삭제 불가(불변)" → 옳게 구현.
  - 창발 C: A ∧ B = **지울 수 없는 감사원장에 아무나 무한히 쓰레기를 쌓을 수 있다.** 무결성 장치가 방어에서 공격면으로 역전.
- **재현**: 익명 POST 21회 → audit_log 21행 주입 → 표적 삭제 시도 시 트리거가 ABORT("삭제 불가") → 정리 불가.
- **수리**: 감사원장엔 '결과 사건'만, 익명 무효 시도는 삭제가능 테이블로 분리. + rate-limit + 중복차단. (실측: 무효 3회에 감사 2→2 불변)
- **함께 나온 결함 7**: fail-open 판정(미지 variant→조용히 안전), parseBig 비문자열 강제변환, 자기이익 스코핑(못 깰 판을 담보 도전처럼 제시 + 허위 경계문구), z3 과장 표기, 시빌·공식 사칭, DoS, variant 노출.

## 교훈 (제품·연구 양쪽)
1. **요구 교차점 리뷰가 별도 게이트다.** 단위 요구 검증만으론 창발 위험을 못 잡는다.
2. **불변성은 무조건 선이 아니다** — 무엇을 불변으로 만들지(결과 vs 시도)를 안 가르면 불변성이 공격면이 된다.
3. **AI 자율구축은 반드시 적대 검증과 짝**이어야 한다(build → red-team → fix). 이것이 세종 체제의 계명 ⑥(AI 변경도 결재·검증)의 실증.
4. 전례 INC-2026-08-29(설계 요원이 자기 결재를 자기가 도장): 같은 계열 — AI가 자기 권한 경계를 스스로 못 지킴.

## INC-2026-09-01-01 — 커넥터 SSRF 방어의 검증-사용 시점차(DNS 재바인딩/TOCTOU)
- **발견팀**: 의료팀(진단, 2026-09-01 스탠드업). 레드팀 실공격 증명은 유보 — 커넥터가 아직 외부 URL을 안 받아 라이브 재현 불가.
- **어디서**: sejong-arena `connector.mjs`(callExternalBot·callKakaoSkill) · `mcp.mjs`(connect) — 세 호출부 동일 패턴.
- **패턴(★ 창발)**: 두 요구를 **각각 옳게** 구현했으나 교차점에서 위험이 창발.
  - 요구 A(SSRF 방어): "고객이 준 URL이 공인 IP인지 검증" → `assertPublicUrl`가 `dns.lookup()`으로 IP를 확인(사설·링크로컬·169.254.169.254·CGNAT·IPv6 ULA 차단, redirect:"error"까지) → 옳게 구현.
  - 요구 B(커넥터): "그 URL로 나가 응답을 받아온다" → `fetch(cfg.url)` → 옳게 구현.
  - 창발 C: **검증(lookup)과 접속(fetch가 호스트명을 다시 해석) 사이의 시간차(TOCTOU).** 공격자 DNS가 검증 땐 공인IP, 접속 땐 사설IP(169.254.169.254)를 돌려주면 정적 검사를 통과하고 내부 메타데이터를 친다. 정적 SSRF 방어가 동적 재해석 앞에서 무력화.
- **왜 거기 있나(근본원인)**: 검증과 사용이 **같은 식별자(호스트명)를 서로 다른 시점에 각자 해석**한다. AI가 "IP를 검증하라"를 '이름→IP 1회 확인'으로 구현했으나, `fetch`는 접속 시 이름을 IP로 **재해석**한다. 검증 결과(IP)를 접속에 **고정(pin)** 하지 않은 것 = 고전 TOCTOU. INC-2026-08-30-01과 같은 계열(각 요구는 옳으나 교차점에서 창발).
- **재현/상태**: 로컬 negative 케이스로 재바인딩 시나리오 확인, 수리(`guardedLookup`+`ssrfAgent`) 로컬 11/11 통과. **그러나 미커밋·미배포 — 2026-09-02 재확인 시 connector.mjs에 guardedLookup 부재(검증된 수리가 워킹트리에서 사라짐).** 현재는 **잠재**(커넥터가 하드코딩 데모봇만 치고 외부 URL 미수용) → 외부 봇 연결 시 라이브.
- **수리(검증됐으나 미배포)**: 검증한 IP를 접속 시점에 **고정** — undici `connect.lookup` 핀 또는 host 핀+`Host` 헤더로 원 호스트명 보존. (redirect:"error"는 이미 적용.)

## 교훈 (INC-2026-09-01-01)
1. **TOCTOU는 '검증'과 '사용'이 같은 이름을 다른 시점에 재해석할 때 창발한다.** IP를 검증했으면 그 IP로 접속해야 한다(이름 재해석 금지).
2. **정적 방어(이름 검증)와 동적 방어(접속 IP 핀)는 별개 게이트다.** 하나만으론 못 막는다.
3. **검증된 수리를 배포하지 않으면 방어가 아니다(미배포 = 미방어).** 노출창이 열린 채 남고, 워킹트리 방치 시 수리 자체가 소실된다(이번 사례).
4. **잠재 취약점도 대장에 선등재한다** — 입력 경로(외부 URL)가 열리는 순간 라이브가 되므로, GateProof 외부 커넥터 상용화의 전제 게이트다.
