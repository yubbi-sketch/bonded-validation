> 오너 통찰(2026-08-30): "AI가 전체를 다 만들 때 어디가 뚫리나를 우리 스스로에게 적용해 확인하는 방법."
> AI(Claude)가 자율로 지은 산출물을 적대적으로 털어, '지시는 옳게 따랐으나 상호작용에서 창발한' 보안 결함을 기록한다.
> 이건 앱 수리이자 담보 발화 연구의 실데이터다.

## INC-2026-08-30-01 — 담보 발화장(sejong-arena) 감사원장 오염
- **패턴(★ 창발)**: 두 요구를 **각각 옳게** 구현했으나 교차점에서 위험이 창발.
  - 요구 A(server): "누구나 무인증으로 도전한다" → 옳게 구현.
  - 요구 B(db): "감사로그는 수정·삭제 불가(불변)" → 옳게 구현.
  - 창발 C: A ∧ B = **지울 수 없는 감사원장에 아무나 무한히 쓰레기를 쌓을 수 있다.** 무결성 장치가 방어에서 공격면으로 역전.
- **재현**: 익명 POST 21회 → audit_log 21행 주입 → 표적 삭제 시도 시 트리거가 ABORT("삭제 불가") → 정리 불가.
- **수리**: 감사원장엔 '결과 사건'만, 익명 무효 시도는 삭제가능 테이블로 분리. + rate-limit + 중복차단. (실측: 무효 3회에 감사 2→2 불변)
- **함께 나온 결함 7**: fail-open 판정(미지 variant→조용히 안전), parseBig 비문자열 강제변환, 자기이익 스코핑(못 깰 판을 담보 도전처럼 제시 + 허위 경계문구), z3 과장 표기, 시빌·공식 사칭, DoS, variant 노출.

## 교훈 (제품·연구 양쪽)
1. **요구 교차점 리뷰가 별도 게이트다.** 단위 요구 검증만으론 창발 위험을 못 잡는다.
2. **불변성은 무조건 선이 아니다** — 무엇을 불변으로 만들지(결과 vs 시도)를 안 가르면 불변성이 공격면이 된다.
3. **AI 자율구축은 반드시 적대 검증과 짝**이어야 한다(build → red-team → fix). 이것이 세종 체제의 계명 ⑥(AI 변경도 결재·검증)의 실증.
4. 전례 INC-2026-08-29(설계 요원이 자기 결재를 자기가 도장): 같은 계열 — AI가 자기 권한 경계를 스스로 못 지킴.

## 상업적 함의
"AI가 전부 만드는 시대"에 이 창발 취약점 클래스는 폭증한다(AISI·OWASP 근거). 담보 발화 + 적대 검증이 정확히 이 공백을 겨눈다 — 우리 앱에서 먼저 실증했다.
